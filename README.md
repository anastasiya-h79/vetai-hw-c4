# Vet AI Assistant — ДЗ по C4 Model (вариант Draw.io + VS Code + GitHub)

## Файлы

- `c2-container-diagram.drawio` — C2: Frontend, Backend, AI Service, Vector DB, SQL DB
- `c3-component-diagram.drawio` — C3: внутренности AI Service (контроллеры, RAG Manager, LLM Client, Prompt Template Factory)
- `sequence-diagram.drawio` — сценарий «Пользователь запрашивает рекомендацию» по шагам
- `openapi.yaml` — спецификация эндпоинта `/get_recommendation`

## Шаг 1 — открыть диаграммы в VS Code

1. Скопируй все три `.drawio` файла в папку своего проекта (туда, где у тебя открыт репозиторий в VS Code).
2. Кликни по любому `.drawio` файлу — если расширение draw.io стоит, он сразу откроется как визуальная схема, не как текст.
3. Посмотри, всё ли на месте. Подвинуть блоки мышкой можно свободно — расположение не влияет на оценку, важны сами блоки и подписанные стрелки (это как раз проверяют по критериям «Соответствие нотации» и «Связность»).

## Шаг 2 — закоммитить и запушить в GitHub

Прямо в VS Code:
1. Открой вкладку **Source Control** (иконка веточки слева).
2. Увидишь новые файлы (`c2-container-diagram.drawio` и т.д.) — поставь галочки / нажми **+** рядом с каждым, чтобы добавить их в коммит (**stage**).
3. Напиши сообщение коммита, например: `add C4 diagrams and OpenAPI spec for HW4`.
4. Нажми **Commit**, потом **Sync Changes** (или **Push**) — файлы уйдут на GitHub.

## Шаг 3 — получить ссылку для сдачи

GitHub не всегда красиво показывает сырой `.drawio` (может показать как текст/XML). Поэтому надёжнее сдать так:

1. В VS Code открой каждую `.drawio`-диаграмму и найди в расширении кнопку экспорта (обычно через **File → Export as → PNG/SVG** в самом редакторе draw.io внутри VS Code, либо иконка экспорта на панели редактора).
2. Сохрани PNG рядом с `.drawio` файлом (например `c2-container-diagram.png`).
3. Закоммить и запушь PNG тоже.
4. На GitHub зайди в файл `.png` — он откроется как картинка прямо в браузере, эту ссылку и отправляй.
5. `.drawio`-файл оставь в репозитории рядом — это «исходник», по желанию можно тоже приложить ссылку на него (как доказательство, что диаграмма редактируемая, а не картинка из интернета).

## Шаг 4 — API-спека

Так же, как диаграммы — закоммить `openapi.yaml` в тот же репозиторий, и дай ссылку на файл на GitHub (или, если хочешь именно Gist — зайди на gist.github.com, вставь туда содержимое файла, Create public gist).

## Ключевые архитектурные решения (для раздела "почему так" в отчёте)

Эти три решения стоит явно проговорить при защите ДЗ — они показывают, что архитектура
не просто нарисована, а обоснована требованиями (как в тезисе "Суть работы архитектора —
Решения, а не Схемы" из вебинара):

1. **Triage Service вынесен в отдельный контейнер, а не компонент внутри AI Service.**
   Причина: неотложные случаи (например, подозрение на непроходимость ЖКТ) не должны
   зависеть от вероятностного вывода LLM. Это простой rule-based слой, который Backend
   вызывает ДО AI Service — если находит red flag, RAG/LLM-пайплайн вообще не запускается.
   Это одновременно быстрее (нет похода к LLM) и надёжнее (нет непредсказуемости модели)
   для самых критичных случаев.

2. **Media Controller (фото/видео) исключён из MVP.**
   Причина: точность анализа изображений сильно зависит от качества фото с телефона
   (свет, ракурс, размытие), и для медицинского контекста риск ложного вывода выше, чем
   польза на первой итерации. Оставлен как явная заглушка на диаграмме — это показывает
   осознанный scope, а не забытую часть.

3. **Lab Results — структурированная форма вместо OCR-распознавания бланков.**
   Причина: автоматический парсинг разнородных бланков лабораторий — отдельная сложная
   задача сама по себе, не критичная для первой версии. Структурированные поля быстрее
   в разработке и не добавляют ещё один источник ошибок распознавания поверх и так
   вероятностного LLM-вывода.
